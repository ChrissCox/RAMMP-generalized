# Fast, accurate execution

Minimize time to first useful motion and avoidable pauses while preserving task success, geometric accuracy and measured safety limits. Plan locally during execution: support continuous motion with bounded in-flight trajectory and endpoint updates within an admitted skill, and prepare subsequent motions ahead. The rolling receiver, guards and simulation tests now implement part of this target; a retained static cuRobo worker now feeds a monitored MuJoCo rehearsal; physical rolling execution remains unavailable. The arm may still need to stop for contact verification, missing evidence, confirmation, faults or unavailable continuation; those causes must be visible in timing traces.

Current code is in [motion/rolling.py](../../rammp_adl/motion/rolling.py), [motion/guards.py](../../rammp_adl/motion/guards.py), [motion/leasing.py](../../rammp_adl/motion/leasing.py), [executor.py](../../rammp_adl/executor.py) and [telemetry.py](../../rammp_adl/telemetry.py). The [runbook](../runtime.md) explains how to reproduce synthetic replacement tests and actual MuJoCo joint-state handoff separately. Fixture timing is not a Jetson performance measurement.

## Changes that fit the current contracts

| Area | Required behavior |
|---|---|
| Startup | Initialize and warm the configured planner before accepting tasks. Reuse planner, camera, model-client and schema resources rather than recreating them per skill. Record cold-start time separately. |
| Perception | Run local tracking and relevant metric updates during motion. Sensor reads are separate from skill claims. Use valid cached evidence until its real validity conditions change. |
| Reasoning | Plan at task start and on relevant events. Use compact current context and avoid unnecessary explicit observations. Existing cloud requests still require verified hold. |
| Dispatch | Start a ready node as soon as evidence, confirmation and resource requirements pass. Replace arbitrary settling sleeps with measured readiness checks where the backend supports them. |
| Gripper | Overlap empty-gripper preshaping and transit when their claims and full aperture collision envelope permit it. Retention verification still precedes carrying. |
| Constraint motion | Follow a continuous cuRobo-generated path with local monitoring and validated updates to its remaining portion. Sampling an arc or advancing the planning horizon does not require a physical stop. Commissioning may use short stopped trials; that is not the normal performance target. |

The final timed/interpolated path must satisfy constraint, collision, velocity, acceleration and stopping requirements. Faster completion must not come from relaxed pose tolerances, unverified grasp success or lower-confidence object associations.

## Updating the active motion while it runs

Use receding-horizon motion planning: execute a validated portion while local cuRobo computation prepares the upcoming portion using current observations. Keep a useful longer route when it remains valid; do not solve the entire task again for every camera frame. Astra still selects skills and task goals. Local motion updates neither call Astra nor rewrite its DAG.

The active move_to_pose or follow_constraint handler retains its ARM, PLANNER and applicable GRIPPER claims. Its own planning work is covered by those claims; it does not need to release them or start a second arm skill. The catalog's curobo_online_replanning and continuous_trajectory_handoff capabilities are NEW project requirements and remain unavailable for deployment. The internal receiver/validation contract and actual MPC integration now have simulation evidence; physical driver handoff integration remains missing. Static trajectories remain useful commissioning tests but do not demonstrate the requested reactive capability.

The complete adapter integration must provide the following behavior before those capabilities are exposed:

1. Read timestamped measured joint state and local target/collision evidence. Account for capture, estimation, planning, validation, transport and driver latency. Estimate joint derivatives with characterized uncertainty where they are not directly measured.
2. Choose a future controller switch point beyond the already committed command prefix. Predict joint position, velocity and acceleration there. Starting a replacement from an old measured position with assumed zero velocity is invalid while the arm moves.
3. Have cuRobo generate a candidate suffix from that moving boundary state toward the current admissible target. Preserve the active skill's constraints, contact allowances, grasp relation and stopping option. Warm-start where the selected cuRobo version supports it.
4. Validate the exact final timed trajectory, its connection to the committed prefix, full-robot/tool/payload collision and stopping envelopes, constraint tolerances, joint/link limits and target provenance. Account for bounded obstacle motion and observation uncertainty over the execution horizon. An optimizer success flag alone is insufficient.
5. Atomically install only an accepted suffix. Bind it to task/node/attempt/epoch, expected active trajectory generation, next generation, switch point, boundary-state tolerances, relevant dependency identities and validation evidence. The driver must acknowledge which generation and switch point it accepted. Recheck measured joint state and relevant evidence at activation, not only when the future suffix is installed. If switch-time tolerances or dependencies fail, reject that generation and use only a still-valid continuation or the verified stop; never splice from an incompatible state. Reject late, superseded, incompatible or out-of-order candidates; never retag old validation.
6. Continue monitoring the currently executable prefix while computing. Keep a bounded committed prefix, sufficient validated lookahead and a commissioned stopping option. If a replacement misses its deadline, continue the existing motion only while its continuation remains valid; otherwise start the verified stop early enough. An invalid current stopping horizon requires immediate supervisor intervention, without waiting for the planner.

Trajectory generations are distinct from execution epochs. A permitted suffix update stays inside the same node, attempt and epoch; cancellation, ownership loss or task replacement revokes all queued generations immediately. A suffix update does not complete the skill or release resources. Perception continues committing measured geometry through the sole world writer; predicted states never become success facts.

### What may change during motion

Trusted local profiles must specify which metric quantities may update, their cumulative correction and uncertainty bounds, evidence requirements, convergence criteria and timing budgets. Derive these settings locally; Astra cannot provide arbitrary moving targets or correction policies. Apply meaningful-change thresholds to avoid chasing sensor noise, without suppressing safety events.

| Change | Required behavior |
|---|---|
| Better pose estimate or bounded movement of the same target | Update its same pose role and remaining trajectory only within the profile's tracking envelope, with fresh identity and collision evidence. |
| Obstacle changes outside the immediately unsafe region | Revalidate the current continuation and plan an admissible updated route while moving where the stopping margin permits. |
| Better articulation estimate during follow_constraint | Permit only locally evidenced refinement within the admitted mechanism type and commissioned envelope. Keep target_value as the original absolute articulation goal; updating its Cartesian realization does not change the requested opening. |
| Target identity ambiguity, excessive displacement, unmodeled contact, slip, invalid calibration/base state or lost protection | Follow the catalog/supervisor stop and recovery policy. Do not invent another object, axis, grasp, task or controller to maintain motion. |

Confirmation must remain valid for the resolved behavior; an update that revokes required assent causes a hold. Routine bounded trajectory refresh is normal control activity, not a failed skill retry or a cloud task replan. An optional candidate can be rejected while a valid continuation exists. Loss of an admissible continuation is a skill failure. Refreshes cannot reset skill deadlines or extend target chasing indefinitely; terminal success still requires current measured goal evidence.

## Preparing a later skill while the current skill runs

Prepare subsequent motion while current validated motion runs where its predicted state and dependencies permit. This is separate from the active handler's internal replanning: move_to_pose and follow_constraint currently claim PLANNER for their entire action, preventing a different handler from borrowing it.

Before enabling preparation of a different skill, define trusted planning/execution phases in the catalog and enforce bounded planner leases in the executor. Retain arm and applicable gripper ownership during execution. Release planner ownership only through that declared protocol; computational idleness alone does not release a claim. Active-motion updates take priority over speculative work. Bound non-preemptible GPU calls so speculation cannot starve continuation, monitoring or stop responsiveness. Never mutate a solver's active world concurrently with an in-flight solve.

The [lease implementation](../../rammp_adl/motion/leasing.py) tests priority and draining of non-preemptible work. The current catalog still reserves PLANNER for the entire skill and does not define phases enabling successor speculation. Therefore the current ADL executor cannot advertise planning a different skill concurrently; active-skill rolling tests and successor planning availability must remain distinct.

A prepared trajectory must carry its predicted handoff state, valid start-state tolerances, exact trajectory identity, relevant scene/calibration/base/tool/attachment/grasp identities, execution epoch and expiration rules. Preparation neither acquires arm ownership nor satisfies predecessor effects. Recheck measured state and relevant dependencies before dispatch; reuse compatible preparation and discard invalid preparation. A change in an unrelated world entry should not force every path to be recomputed.

This initially requires project-owned internal adapter contracts. Existing ValidatePlan/ExecuteSkill fields do not by themselves establish speculative planning or trajectory reuse. Do not invent upstream endpoints or silently execute a different path from the one checked.

## Continuity and boundaries

A single follow_constraint action should execute continuously with rolling updates as specified above. Prove position/velocity/acceleration continuity, sufficient validated lookahead and bounded stopping on buffer underrun before using it. Computational horizons are not skill boundaries.

The current cross-skill contract requires backend quiescence before terminal effects commit and claim release. Minimize software delay at those boundaries; do not claim nonzero-velocity blending across them. Such blending needs a separate ownership, evidence and cancellation protocol plus verified planner/driver handoff support. The pinned planner action documents start_joints, not a velocity/acceleration continuity guarantee.

## cuRobo integration and remaining work

Use cuRobo for all arm path generation. Its documented MPC interface supports updating goals and optimizing from current joint state; the documented solver is local and can become stuck. The relevant documentation also describes MPC as experimental and collision constraints as weighted costs, so it is an implementation candidate requiring independent trajectory checks and simulation, not a complete safety mechanism. [MPC interface](https://curobo.org/_api/curobo.wrap.reacher.mpc.html), [MPC example and limitations](https://curobo.org/get_started/2a_python_examples.html#model-predictive-control-mpc)

The [optional static adapter](../../rammp_adl/motion/curobo.py) pins the RAMMP source and checks the expected cuRobo version/import origin before use. It has run on this Jetson in an isolated cuRobo 0.7.8 GPU environment and explicitly rejects a moving q/dq/ddq boundary. The [retained worker](../../rammp_adl/motion/curobo_process.py) initializes once, serializes requests, pins read-only assets and bounds protocol I/O. Cancellation drains non-preemptible work; a failed Docker teardown retains the solver lease until container quiescence is positively verified. Actual warm static solve timings and separate initialization costs are in [Jetson results](../jetson.md). This does not establish a moving-boundary solver or cross-skill planner lease. The required rolling/constrained extension must use a verified compatible API rather than mix newer examples with the pinned wrapper. MotionGen can provide a longer route where supported; selecting MPC does not establish arbitrary contact-path or global routing capability.

The pinned RAMMP wrapper exposes MotionGen actions but no MPC or rolling replacement interface. The implementation now includes an optional direct `CuroboMpcAdapter` and a [local rolling session](../../rammp_adl/motion/session.py). The session overlaps candidate generation/independent validation with tracking, checks the full active skill's resource ownership, binds pending candidates to the target and world, and starts stopping when a planning deadline expires while retaining the nonpreemptible worker lease. Actual cuRobo 0.7.8 GPU moving-boundary output has now been independently screened and passed into that session against MuJoCo dynamics. Contact validation, continuous stopping envelopes and physical driver integration remain unverified; these modules do not enable hardware or cross-skill blending.

The pinned MPC default state filter altered the incoming derivatives. The adapter explicitly disables that filter, requests fixed command time steps, preserves every GPU-returned state and checks the initial q/dq/ddq boundary. A full optimized horizon can now be returned in one solve; unsupported moving-goal callbacks are rejected in this mode. Independent interpolation checks exposed acceleration overshoot despite acceptable knot values. The simulation probe addresses this through tighter cuRobo optimizer acceleration limits; it does not overwrite derivatives, retime a moving suffix or weaken independent bounds. A separate stationary-start reference uses the pinned wrapper's consistent time dilation.

The [accepted GPU/MuJoCo rehearsal](../../artifacts/jetson/independent-readiness/reactive-final-2/rolling-rehearsal.json) activated a new generation during a bounded 5 mm same-target correction and kept tracking commands active during the recorded GPU solve. Existing simulated activation/tracking bounds were unchanged. Intentional cancellation retained ARM/PLANNER through GPU drain and measured settling. No generated stop trajectory was admitted: the simulation supervisor froze its actuator setpoint, and the report records failed/cancelled execution instead of task success. Earlier failures remain recorded. These single-run timings are diagnostic Jetson observations, not commissioned deadlines or a throughput benchmark.

A second [actual solver cancellation](../../artifacts/jetson/independent-readiness/reactive-final-2/rolling-cancel-during-gpu.json) records cancellation between entry and return of the cuRobo solver call, without injecting a GPU delay. Its unactivated suffix is discarded. Planner work drains, and current MuJoCo physics must supply a measured stationary dwell before claims are released; time spent waiting for GPU work cannot refresh an old state. The [shared GPU lease journal](../../rammp_adl/motion/gpu_lease.py) persists the owned container name before launch. Both static and reactive Docker clients inherit the cache lock. After a client crash, another process refuses cache reuse until the exact recorded container is positively absent; it never adopts or removes a prior process's container.

## Measurement and acceptance

Log command receipt, first useful motion, planning/validation durations, node readiness/dispatch, motion intervals, evidence acquisition, effect commits, task outcome and each wait reason. For rolling updates, log observation age, predicted/actual switch state, candidate acceptance/rejection, trajectory generations and remaining validated lookahead. Separate cloud waiting, planning, resource contention, observation, gripper/contact verification, user confirmation, safety stopping and recovery.

Report median and tail task latency, avoidable idle time, transition latency, planning headroom and task success/accuracy on the same scenarios. Count gripper work and required sensing as useful task activity; arm movement percentage alone must not reward unnecessary paths. Establish numerical budgets from the actual Jetson/driver measurements rather than promise an unsupported update rate or zero idle time.

Required reactive-motion validation includes a bounded same-object target shift during transit, supported articulation refinement, a newly relevant obstacle, delayed/out-of-order planner results, discontinuous candidate rejection, expired evidence, buffer depletion, cancellation during replacement and excessive target motion. Protocol/guard tests cover these rejection and handoff cases with explicit synthetic trajectories and evidence. MuJoCo replay additionally checks replacement against simulated Gen3 joint motion. Neither establishes that cuRobo can generate the necessary ADL continuation or that physical contact, payload and stopping envelopes are safe. Integrated ADL physics and hardware commissioning remain separate work.
