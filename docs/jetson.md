## Motion layer remodelled on the planner's real output, 2026-09-21

The second armed run reached `RUNNING` and failed its first motion node three times with `planning_failed: Waypoint 0 has no acceleration profile` ([log](../artifacts/jetson/first-armed-run-2026-09-21/node-second-run.log)); the arm did not move. The client demanded a trajectory the planner never produces. A plan-only probe against the live planner and RAMMP-CuRobo v1.0.0's `conversions.py` agree: waypoints carry positions and velocities and no accelerations, and waypoint k is stamped at (k+1)*dt with waypoint 0 equal to the start state. The box-opening client that already drives this arm sends exactly that to the driver. Every earlier test of this boundary used hand-built trajectories, so nothing had caught it.

At the user's direction the motion method was compared with [RAMMP-Kinova](https://github.com/ChrissCox/RAMMP-Kinova) (cuRobo, MuJoCo, a tool-calling brain) and remodelled on it where the real deployment allows:

- **The wire is what the planner gives.** The canonical trajectory takes the start state at t=0 at rest and accelerations differenced from the planner's velocity profile, both named in its provenance; the message to the driver leaves both out, so the driver receives the planner's own waypoints and stamps, time-scaled. The probe now passes the live planner's output through the client path with no refusal (31 waypoints, 0.62 s, 1.55 s at the transit scale, wire velocities only). Nothing was executed.
- **Settle, then judge arrival.** The driver reports success as its reference ends; one look then could read "moving" and fail a good motion. The client now waits up to 6 s for a still window, fails closed, and then checks arrival within 0.02 rad.
- **Leaving a contact.** A move that departs from a grasp pose exempts the tool's own neighbourhood from the depth guard for that move only, as the reference exempts a touched prop only while leaving it.
- **Backing out.** When the planner refuses the start as in collision, the backend retraces the last completed path once, empty-handed and under the guards, and plans again. Nothing new is planned for the way out. The match on the planner's status text is marked TODO: confirm against planner.
- **Miss, jam, reopen.** A close that stalls almost open is reported as fingers pressing on the part; a miss or a jam reopens the hand so the retry starts as the plan expects.
- **One retry per failing idea.** The same skill failing with the same code and detail after a replan ends the task with that reason instead of spending the remaining replans and requests; the plan rules tell the model that feedback is what really happened and to change the approach once.

Not adopted: voice control (excluded by the user), the reference's tool-by-tool brain loop (this project plans a validated DAG and replans on failure), `velocity_scale` fixed at 1.0 (a simulator actuator limit; here trajectories are only ever slowed), and in-process cuRobo world updates (the planner is a container; its world is set through `set_world`, which this client does not yet call).

All **672 unit tests passed**; the design checker passed. The arm has still not moved: no trajectory has yet been sent to the driver by this client.

## Why the final approach always tripped, 2026-09-24

Every armed run since 2026-09-21 stopped on the collision guard during the move from the standoff to the grasp pose, whether or not model alignment had converged. Offline, with the live planner planning the same approach and the guard's own sphere model placed along it against the measured door, the cause is in the grasp, not the guard. `pose_roles` put the planner's tool frame 1.6 cm off the door face, half the pull's 3.2 cm protrusion, but the tool frame (end_effector_link + 0.12 m) is the root of the 2F-85 pads: the finger-tip collision meshes of the locked assembly reach 4.6 cm past it. The plan drove the fingertips 3.0 cm into the door, and the guard was right to stop it. Top-down grasps now keep the tool frame at least 4.6 + 1.0 cm above the surface the part stands on, so the distal pads pinch a shallow pull with the tips a centimetre off the door. The guard's fingertip spheres are 3.5 cm with a 3 cm margin, so even a correct grasp reads the door face just beyond the 10 cm target ball as an obstacle (2.8 cm): the final approach and the move leaving the handle now also exempt the measured surface under the target, a disk of 11 cm and nothing more than 2 cm proud of it, held in the tool frame so it follows a door that moved with the hand. With both, the offline check finds no intrusion anywhere along the approach. Alignment now treats a model nudge under 8 mm and 3 degrees as centred rather than spending the task's request budget on it. Not yet run on the robot.

The deployment manifest's update of 2026-09-23 removed the adl node, which only ever existed as a local edit. Its definition now lives in [deployment/sheppy/adl-node.yaml](../deployment/sheppy/adl-node.yaml) and `tools/sheppy_adl_node.py install --armed` puts it back.
