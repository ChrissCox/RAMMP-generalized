# Repository instructions

This repository contains the design, machine-readable contracts and a Python autonomy runtime for generalized ADL manipulation on a Kinova Gen3. The runtime runs in two compositions. The fixture composition executes the six catalog skills against an explicit synthetic backend, with MuJoCo joint-physics and GPU rolling rehearsals beside it. The sheppy composition is a client of the december_2026 sheppy deployment: it plans through the RAMMP-CuRobo container, executes through the kinova-gen3-ros2 driver container, grounds untagged objects by sending still wrist keyframes to gpt-6-astra and placing them with local depth, and follows model-proposed constraints recorded under artifacts/constraints/. The operator has authorized physical motion and wrist-image egress for that composition; both stay off unless the manifest sets commissioned and arm_motion. No physical run has been validated yet. Do not present fixture outcomes, joint replay, ROS source checks or mocked provider responses as robot validation. Read docs/runtime.md and docs/hardware-testing.md for commands and verified limitations.

Read docs/project-prompt.md and docs/design/00-README.md. Read the relevant design section before implementing it. Use these authorities without copying competing definitions:
- skills/adl_skill_library.yaml: fixed skill IDs, typed args, resource claims, capability gates, predicates, failure policy.
- schemas/plan.schema.json and schemas/reasoning-response.schema.json: generated plan/response grammar; regenerate with python tools/check_design.py --generate after catalog edits.
- interfaces/: canonical project-owned ROS IDL with build packaging, not existing upstream APIs; ROS compilation remains a separate check.
- docs/design/00-interface-fact-sheet.md: source-pinned external facts and outstanding deployment checks.
- config/reasoning.json: OpenAI gpt-6-astra selection, effort tiers and bounded cloud settings.
- config/sheppy-bench.context.json and config/imagery-locality.json: the bench's physical profiles and the deployment's routable camera domain.

Task-specific sequencing belongs in plans. Reusable physical behavior belongs in implemented skills. A YAML declaration never auto-creates a handler. Never generate executable code, arbitrary predicates, resource claims, safety limits, or retry policies from model output. The model names objects, marks boxes and grasp points, proposes a constraint's parameters and nudges a grasp target in bounded steps; metric poses, planning, guards and every world fact stay local. Register only implemented, tested capabilities; capabilities this client cannot provide are declared by the operator as acknowledged gaps and logged at startup.

Implementation lives in rammp_adl/. The live path is ros_node, intake, reasoning, executor, validation, world, sheppy_backend, constraints, motion/sheppy_arm, motion/sheppy_client, motion/collision_guard, motion/kinematics and perception/{grounded_scene, keyframes, object_geometry, ros_rgbd, ros_locality, images}. Keep fixture capability emulation explicit and separate from deployed capability evidence. MuJoCo joint stimuli exercise physics and the rolling receiver protocol; they are not a replacement arm planner. Frames leave the machine only as screened, downscaled keyframes; never upload a frame the face screen has not cleared.

Prioritize fast, accurate execution with minimal avoidable idle time; follow docs/design/14-performance.md. Keep computation warm and local perception active. Keep model requests short: one persona, a compact scene brief, generated skill cards, low reasoning effort, and no provenance the model cannot use. Never run blocking work on the runtime loop; the supervisor's status tick and the cloud hold guard depend on it.

Use cuRobo for arm IK and trajectory generation. The driver tracks validated cuRobo joint trajectories. The planner container plans from a stationary start only: constraint following is a sequence of such plans under an effort budget, and must be described as that, not as a constrained or continuously replanned path. Learned policies (for example ACT or Diffusion Policy) trained on this robot's own demonstrations may command the arm, but only inside an implemented skill's contact phase that starts from a cuRobo-reached pose: every action chunk goes to the driver as a trajectory through the same send gates and guards as any other, the skill's postconditions are still established by measurement, and a policy is registered for a skill only after it passes on the real bench. Outside that, do not bypass missing planner support with hand-written IK, Cartesian servo loops, untrained or unregistered policies, or automatic controller fallback.

Unknown upstream calls must be labeled "TODO: confirm against driver" (or planner); project-owned proposed interfaces are explicitly NEW. Do not remove unresolved engineering dependencies to make the design look complete.

Run python tools/check_design.py and python -m unittest discover -s tests -v after contract changes. Preserve originals of modified files under .audit-backups/<task>/, markdown as .md.bak. Hardware, ROS compilation, provider access, and Jetson benchmarks are separate checks and must be reported honestly. No unavailable external coding skill is required.
