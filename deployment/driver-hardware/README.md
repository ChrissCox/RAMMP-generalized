# Instrumented Kinova driver

This directory prepares isolated pinned source copies and adds the project's explicit driver extension. The existing upstream workspaces are not patched. See [physical testing instructions](../../docs/hardware-testing.md) for commands and qualification limits.

Pins are declared in [prepare.py](prepare.py). Both SimTransport and physical Kortex paths pass through `FeedbackProbe`; a successful exchange advances the feedback sequence/timing. The canonical NEW messages are [DriverFeedback](../../interfaces/msg/DriverFeedback.msg) and [DriverHeartbeat](../../interfaces/msg/DriverHeartbeat.msg), published on `/rammp/driver_feedback` and `/rammp/driver_heartbeat` with reliable/volatile QoS. They use same-host Linux CLOCK_MONOTONIC and boot/session identity. They do not claim a device acquisition timestamp or acceleration measurement.

The current overlay uses custom ROS driver revision `3337456a1e6062969934174091b3e0ce1bb55f9c`, matching the inspected installed source files, and `rammp-interfaces-ros2` revision `38b326451ce289e0e3a473fee77a9be4cedeffa1`. Its action comes from `rammp_arm_interfaces`; ownership, status and software stop come from `rammp_common_interfaces`. The source manifest hashes the consumed action/service/message definitions. Rebuild into a fresh workspace after this migration; the old `kinova_gen3_interfaces` build is not the new command transport's dependency. No running deployment is modified by preparing or compiling this overlay.

`GuardedOwnership` wraps the sole ROS owner-management path, refuses an acquire while already owned, and preserves the existing release token after a denied claim. Heartbeats bind owner/token/generation to source session, host boot, monotonically increasing sequence and sender time. A separate C++ thread latches the core stop on expiry; a main-loop heartbeat thread cannot hide a stalled Python monitor. This is an independent thread in the driver process, not a hardware safety controller. Complete driver-process/OS loss still requires the physical controller's commissioned watchdog/stop behavior.

[build.py](build.py) compiles only; neither mode launches a driver. Hardware mode requires an explicit Kortex SDK and inspects/hashes its AArch64 archive. The test reproducer [test_transport.py](test_transport.py) refuses a Kortex-enabled build and launches only `--sim`. The native [guard tests](driver_guard_test.cpp) check exchange freshness, non-stealing grants, invalid/replayed heartbeat rejection, latching and stop dispatch while another core command is blocked.

The DDS reproducer remaps every endpoint it uses into a fresh random namespace as well as using localhost domain 91. The physical CLI similarly requires a dedicated explicitly remapped driver namespace; it never falls back to global command services.

The [source comparison](../../artifacts/jetson/real-world-ready/driver-split/source-contract-review.json) and [simulation build manifest](../../artifacts/jetson/real-world-ready/driver-split/sim-build-manifest.json) record the exact revisions and executable identity. These checks do not measure physical stopping or tracking; SimTransport arm feedback remains fixed.

The same overlay also passed [physical-capable compilation](../../artifacts/jetson/real-world-ready/driver-split/hardware-build-manifest.json) against the local Kortex 2.8.0 AArch64 SDK at `/tmp/rammp-driver-split-hardware`. Its executable was not launched. The [migration summary](../../artifacts/jetson/real-world-ready/driver-split/summary.json) separates source/type checks, isolated DDS checks and physical qualification limits.

The overlay does not add a rolling-trajectory action or change interpolation: supplying full q/dq/ddq uses the pinned driver's existing quintic Hermite interpolation. Hardware execution uses position tracking and does not fall back to impedance, torque, velocity or Cartesian control. The current ADL ROS node remains fixture-only.

The gripper extension adds a latched halt below `GripperController`, at the actual transport boundary. The pinned upstream `release()` stops stamping new gripper fields but Kortex continues retransmitting its persistent last target. Therefore stopping the upstream arm controller alone does not establish a gripper stop. The extension replaces a commanded gripper's outgoing target with its last measured normalized position, zero speed, and the previous commanded current ceiling. It never substitutes a default open target or invents a ceiling for an uncommanded gripper. The NEW feedback fields acknowledge this replacement only after a successful exchange; they do not prove physical stopping.

`GuardedGripperSink` records command admission under the same arbiter token gate before a command reaches RT stamping. On revoke, e-stop or heartbeat expiry, new gripper targets remain inhibited. After any admitted gripper command, that halt also refuses a new ownership grant until the driver process is restarted. This is an explicit current limitation: an ownership release is terminal for that gripper driver session, not an internal skill boundary. The full task must retain its shared machine grant through internal skill completions. Arm-only sessions that never admitted a gripper command preserve normal release/reacquire behavior. No old gripper target is restored automatically.

The [calibrated aperture adapter](../../rammp_adl/motion/gripper.py) uses the exact split `GripperSetpoint` message and acquisition-stamped extension feedback. It requires an explicit monotone measured aperture table and bounded calibration error, acquisition age, speed/current ceilings, position tolerance, acceleration, settling and stop deadlines. Simulation tables cannot be used in physical mode. Meter commands are mapped and quantized to the exact float32 values before admission. Current remains in amps; the message field named `force` is a normalized motor-current ceiling. Aperture/current alone never establishes retention, support or release, and this adapter does not enable a physical catalog skill.

The new [gripper DDS test](test_gripper_transport.py) launches only a manifest-matched Kortex-disabled SimTransport executable, with isolated endpoints. After building this overlay, run:

```zsh
export PYTHONNOUSERSITE=1 ROS_LOCALHOST_ONLY=1 ROS_DOMAIN_ID=93
source /opt/ros/humble/setup.zsh
source /tmp/rammp-gripper-driver-sim/install/setup.zsh
source .venv/bin/activate
python deployment/driver-hardware/test_gripper_transport.py \
  --workspace /tmp/rammp-gripper-driver-sim \
  --output artifacts/manual/gripper-dds
```

The output must be new. This checks actual generated DDS command/feedback, simulated aperture completion, cancellation, successful halt exchange, measured settling and rejection of a fresh grant after gripper halt. SimTransport uses its upstream synthetic gripper model, whose effort/contact behavior is explicitly unsuitable for calibrating physical grasp retention. The [serialization check](test_gripper_serialization.py) starts no ROS node and independently verifies exact normalized command/current-ceiling/token fields and halt acknowledgement serialization.

The [measured gripper backend](../../rammp_adl/hardware_gripper.py) connects this gateway to the existing canonical `SetGripperHandler`, local DAG validation and the sole WorldModel writer. Its dispatch artifacts bind the exact aperture, calibrated profile, world/collision/calibration/attachment/grasp identities, task/node/attempt/epoch and GRIPPER ownership. The gateway checks these bindings before each publication. Successful effects contain only measured `aperture_reached` evidence after quiescence; cancellation cannot publish success even if it arrives at the transport-completion boundary. Physical catalog entries and the supervisor's physical dispatch gate remain disabled. Geometry approval, measured empty-gripper state and a shared supervisor heartbeat that reflects all active work are required inputs; the backend does not fabricate them.
